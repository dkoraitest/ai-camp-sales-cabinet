# Архитектура: как подключить свои системы

Кабинет намеренно сделан примитивным — один HTML-файл без сборки и зависимостей. Это не ограничение прототипа, а решение: такой кабинет открывается на любом компьютере через год, когда любой современный фреймворк уже потребует обновления.

При этом архитектура рассчитана на то, что демо-данные однажды заменят на боевые.

---

## Как собирается кабинет

Кабинет не пишется руками и не лежит в репозитории готовым. Он собирается скриптом из заготовок:

```
blocks/_core.html     каркас: DataSource, роли, общие функции, стили
blocks/me.js          вкладки менеджера: Мои сделки, Мои звонки, Мой тренер
blocks/overview.js    дашборд руководителя
blocks/contacts.js    коммуникации
blocks/insights.js    инсайты
blocks/managers.js    команда
blocks/leads.js       лиды
blocks/deep.js        глубокая аналитика
```

`scripts/build_cabinet.py` склеивает каркас и нужные вкладки в `cabinet/index.html`. Кабинет растёт по шагам: шаг 1 собирает `me, overview, contacts, insights`, шаги 2-4 добавляют `managers`, `leads`, `deep`. Что собрано, помнит `cabinet/.blocks.json`, пересобрать то же самое — `--rebuild`, собрать в другую папку — `--out demo`.

Рядом с `index.html` лежат данные, каждый файл подключается тегом `<script>`, а не `fetch()`: кабинет открывается как `file://`, и браузер запрещает ему читать соседние файлы запросом.

| Файл | Откуда | Что в нём |
|---|---|---|
| `data.js` | `scripts/build_data.py` из `data/*/dataset.json` | сделки, разговоры, команда |
| `config.js` | шаг 0 | профиль, воронка, матрица |
| `scores.js` | шаг 1: код + модель | оценки контактов и инсайты |
| `aggregates.js` | шаг 1: `scripts/score_all.py` | разрезы для графиков, пишет код |
| `coach.js` | шаг 2 | карта навыков, разбор, тренировки |
| `telegram.js` | `scripts/telegram.py` | имя бота и кто подключён, без токена |
| `enrich.js` | шаг 3 | следующее касание, обогащение |
| `deep.js` | шаг 4 | выводы глубокой аналитики |

## Где проходит граница

Весь код, который знает, *откуда* берутся данные, собран в одном объекте `DataSource` в `blocks/_core.html`:

```js
const DataSource = {
  profile(){ … },
  calls(){ … },       // звонки
  chats(){ … },       // переписка
  leads(){ … },       // сделки и заявки
  managers(){ … },    // команда
  contacts(){ … },    // звонки и переписка одним списком
  scores(){ … },      // оценки (шаг 1)
  aggregates(){ … },  // разрезы для графиков (шаг 1)
  coaching(){ … },    // тренер (шаг 2)
  enrichment(){ … },  // касание и обогащение (шаг 3)
  deep(){ … }         // глубокая аналитика (шаг 4)
};
```

Интерфейс обращается к данным только через эти методы. Чтобы перейти с демо-файлов на свою систему, меняются тела методов или, проще, скрипт, который пишет `data.js`. Вкладки, таблицы и модалки не трогаются.

CRM подключается скриптом, не браузером: API CRM → `data/own/dataset.json` → `build_data.py`. Ключи API остаются в `.env` и не попадают в страницу. Контракт и заготовки — в `connectors/`.

## Три уровня подключения

### Уровень 1 · Ручная выгрузка (с этого начинают все)

Раз в неделю выгружаете разговоры и сделки, приводите к формату `data/<profile>/dataset.json`, пересобираете:

```bash
python3 scripts/build_data.py
```

Занимает пятнадцать минут, не требует ни доступов, ни разработки. Для первых недель этого достаточно — вы поймёте, какие критерии работают, прежде чем вкладываться в интеграцию.

### Уровень 2 · Экспорт по расписанию

Скрипт, который забирает данные из CRM по API и пишет тот же `dataset.json`, запускается по расписанию. Кабинет об этом ничего не знает — для него ничего не изменилось.

Точка входа — `scripts/build_data.py`. Функция та же: на входе ваши сущности, на выходе `cabinet/data.js`.

### Уровень 3 · Живые данные

`DataSource` ходит в ваш бэкенд напрямую:

```js
const DataSource = {
  async calls(){
    const r = await fetch('https://ваш-сервис/api/calls', {
      headers: { Authorization: `Bearer ${TOKEN}` }
    });
    return r.json();
  },
  …
};
```

Здесь появляется то, чего нет в прототипе: авторизация, права доступа (менеджер видит свои разговоры, руководитель — все), хранение токенов. Открыть такой кабинет двойным кликом уже не получится — нужен хостинг.

**Переходите на этот уровень, только когда первые два перестали справляться.** Обычно это происходит, когда кабинетом начинают пользоваться больше трёх человек ежедневно.

## Что понадобится помимо кабинета

Прототип начинается с готовых текстов разговоров. В реальности до них ещё нужно дойти:

| Что | Зачем | Чем закрывается |
|---|---|---|
| Запись звонков | Без записи нечего анализировать | Телефония, IP-АТС |
| Расшифровка речи | Текст вместо аудио | Speech-to-text сервис |
| Разделение говорящих | Понять, где менеджер, где клиент | Диаризация |
| Привязка к сделке | Иначе разговор висит в воздухе | Интеграция с CRM |
| Хранение | Разговоры — персональные данные | Своя база, политика хранения |

Это отдельный контур, и он строится один раз для всей компании, а не под конкретный отчёт. Кабинет садится сверху.

## Формат данных

Минимальный набор полей, на который рассчитан интерфейс.

**Разговор:**
```json
{
  "id": "c01",
  "date": "2026-09-01T10:12:00",
  "manager_id": "m2",
  "lead_id": "l03",
  "stage": "discovery",
  "direction": "outbound",
  "duration_min": 14,
  "outcome": "краткий итог одной строкой",
  "transcript": [{ "who": "manager", "text": "…" }, { "who": "client", "text": "…" }]
}
```

`who` принимает значения `manager` и `client` — от этого зависит отрисовка реплики.

**Два поля, на которых держится вся склейка.** У разговора есть `lead_id` — с кем
он был, и `stage` — этап, **на котором он произошёл**. У сделки свой `stage` — тот,
где она стоит сейчас. Из этой пары собирается путь сделки: группируем коммуникации
по `lead_id`, внутри — по `stage`, по дате. Переход на новый этап отдельно нигде не
хранится, он и есть первый разговор на этом этапе.

Если ваша CRM отдаёт дату смены стадии — тем лучше, но без неё кабинет обходится.
А вот без `lead_id` не обойдётся: без него звонок и переписка остаются двумя
несвязанными строками, и вопрос «сколько раз мы говорили, прежде чем проиграли»
теряет ответ. При выгрузке это первое, что нужно проверить.

**Лид:** обязательны `id`, `stage`, `source`, `value_kzt`, `owner` (ответственный). Желательны `next_step` (дата) и `created`. Для B2B — `company`, `contact`, `position` и `events` (внешние события: `date`, `type` = news / vacancy / tender, `title`, `source`). Остальные поля произвольны.

**Менеджер:** `id`, `name`, `role`.

Этапы воронки и их подписи задаются в `profile.stages` и `profile.stage_labels` внутри датасета. Свои этапы описываете там же — интерфейс подхватит.
